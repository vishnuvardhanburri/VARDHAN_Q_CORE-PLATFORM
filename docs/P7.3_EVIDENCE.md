## 1. Summary

P7.3 implements **Raft-committed signed ledger checkpoints** with full
adversarial validation. The checkpoint is a signed commitment to a Merkle
root over a contiguous range of ledger entries, replicated via the Raft log,
and persisted to `checkpoints.jsonl` only after quorum commit.

The evidence chain from ledger entry to independent verification:

```text
 Ledger Entries
      │
      ▼
 Deterministic Ledger Sequence          (seq = 0, 1, 2, ... — NOT Raft log index)
      │
      ▼
 Deterministic Merkle Commitment         (BLAKE3(seq || entry_data))
      │
      ▼
 ML-DSA-87 Signed Checkpoint
      │
      ▼
 Raft Replicated Checkpoint Entry       (LogEntry with CHECKPOINT_CLIENT_ID)
      │
      ▼
 Quorum Commit                          (≥ 2 of 3 nodes acknowledge)
      │
      ▼
 Cross-Node Persistence                 (checkpoints.jsonl on all nodes)
      │
      ▼
 pq_verify                               (independent signature + Merkle + chain verification)
```

## 3. Three Bugs Discovered During Adversarial Testing

### Bug #1: Non-deterministic Merkle root (affects cross-node consistency)

**Symptom:** `apply_checkpoint_entry` rejected committed checkpoints on
follower nodes with `Checkpoint Merkle root mismatch`.

**Root cause:** The Merkle root was computed from
`canonical_hash(seq, timestamp_ms, event_json, prev_hash)`. The `timestamp_ms`
field uses `SystemTime::now()` — different on each node. The `prev_hash` field
chains to the previous `LedgerBlock`, which also includes the timestamp.
This means identical ledger entries produce different hashes on different
nodes, so the Merkle root in the leader-generated checkpoint never matches
the follower's locally-computed Merkle root.

**Fix:** Changed to `BLAKE3(seq || entry_data)` for the Merkle commitment.
This is a **deterministic** function of the entry's raft log position and
raw data — identical on all nodes regardless of wall-clock time or signing
identity.

**Scope:** This is the **checkpoint Merkle commitment function**, distinct
from the audit ledger's hash-chain canonical hash (`canonical_hash(seq,
timestamp_ms, event_json, prev_hash)`). The audit chain continues to use
timestamps and signatures for tamper-evident append-only integrity. The
Merkle commitment is the **consensus-level** proof that all replicas agree
on the same entry set.

**Files changed:**
- `ha_cluster/src/raft.rs` — `apply_committed_entries` (Merkle hash computation)
- `audit_ledger/src/lib.rs` — `merkle_root_from_ledger_file`
- `pq_verify/src/main.rs` — Merkle root reconstruction from `ledger.jsonl`

### Bug #2: Ledger sequence vs Raft log index divergence

**Symptom:** After a checkpoint entry occupied Raft log index 4, the next
regular entry at Raft log index 5 produced `LedgerError::InvalidBlockHash`
because `block.index` (= 5 - 1 = 4) did not equal `write.len()` (= 3, since
only 3 regular `LedgerBlock`s existed — checkpoint entries don't create
blocks).

**Root cause:** `LedgerBlock::new` was called with `index - 1` (raft log
index minus 1). This couples the audit-chain block index to the Raft log
namespace. Checkpoint commands occupy Raft log positions but are NOT ordinary
ledger entries and do NOT consume ledger sequence numbers.

```text
Raft log:
  index 1 — regular entry  → LedgerBlock index 0
  index 2 — regular entry  → LedgerBlock index 1
  index 3 — regular entry  → LedgerBlock index 2
  index 4 — checkpoint entry → NO LedgerBlock (ledger_seq unchanged)
  index 5 — regular entry  → LedgerBlock index 3 (NOT 4)

  ledger_seq ≠ raft_log_index - 1
```

**Fix:** Changed to use `ledger_seq` (a counter that increments only for
regular entries) as the `LedgerBlock` index:

```rust
// Before:
ledger_sync::LedgerBlock::new(index - 1, ...)

// After:
ledger_sync::LedgerBlock::new(seq, ...)  // seq = ledger_seq, 0-based per regular entry
```

**Files changed:**
- `ha_cluster/src/raft.rs` — `apply_committed_entries`

### Bug #3: Idempotency check falling through

**Symptom:** `raft_l3_replication::test_replication_basic` failed with
`ledger.len() == 2` instead of `1` — a duplicate `(client_id,
request_id)` pair was applied twice to the ledger.

**Root cause:** The `apply_committed_entries` idempotency check detected
duplicate entries in `applied_requests` but **did not skip** them. It set
`last_applied = index` and then fell through to create a second
`LedgerBlock`, corrupting the audit chain:

```rust
// Before (BUG):
if applied.contains_key(&(client_id, request_id)) {
    *la = index;
    // ← falls through! creates a duplicate LedgerBlock
}
// ... proceeds to create block, add to ledger, etc.
```

**Fix:** Added `continue` after the idempotency check:

```rust
// After (FIXED):
if applied.contains_key(&(client_id, request_id)) {
    *la = index;
    drop(applied);
    drop(la);
    tokio::task::yield_now().await;
    continue;  // ← skip all processing for already-applied entries
}
```

**Files changed:**
- `ha_cluster/src/raft.rs` — `apply_committed_entries`

## 4. Architecture: Four Integrity Layers

### Layer 1 — Ledger Integrity (Audit Chain)

```text
entries ─→ hash chain ─→ tamper detection
```

Each `LedgerBlock` contains: BLAKE3 hash, `prev_hash` linking to the
previous block's hash, and ML-DSA-87 signature over the block hash.
This is the **audit trail** — any modification to an entry or block
breaks the chain. Independently verified by `pq_verify`.

**Function:** `LedgerBlock::verify(dsa_pub_key)`
**Used by:** `MerkleLedger::append_block`, `pq_verify`

### Layer 2 — Checkpoint Integrity (Merkle + Signature)

```text
ledger range ─→ deterministic Merkle root ─→ ML-DSA-87 signature ─→ checkpoint chain
```

The checkpoint covers a contiguous range of ledger entries. The Merkle
root is computed from `BLAKE3(seq || entry_data)` — deterministic, so
all replicas derive the same root. The root is signed by the leader's
ML-DSA-87 key. Checkpoints chain together via `previous_checkpoint_hash`.

**Canonical format:**
```
cluster_id_len(u32 BE) || cluster_id_utf8 || config_epoch(u64 BE)
  || raft_term(u64 BE) || raft_log_index(u64 BE)
  || ledger_first_seq(u64 BE) || ledger_last_seq(u64 BE)
  || ledger_entry_count(u64 BE) || merkle_root(32B)
  || prev_checkpoint_hash(32B) || timestamp_ms(u64 BE)
  || version(u32 BE)
```

**Functions:** `Checkpoint::canonical_bytes()`, `Checkpoint::canonical_hash()`,
`Checkpoint::create_and_sign()`, `Checkpoint::verify_signature()`

### Layer 3 — Consensus Authority (Raft Quorum)

```text
checkpoint ─→ Raft log ─→ replication ─→ quorum ─→ commit
```

The checkpoint is submitted as a `LogEntry` with `client_id =
CHECKPOINT_CLIENT_ID`. It becomes authoritative only after Raft quorum
commit (≥ 2 of 3 nodes acknowledge). Only committed checkpoints are
persisted to `checkpoints.jsonl`.

**Quorum formula:** `(match_indices.len() + 1) / 2 + 1`
- For 3-node cluster: `(2 + 1) / 2 + 1 = 2` (leader + 1 follower)
- Leader's own log entry counts as 1 vote

**Functions:** `LedgerApplier::generate_and_submit_checkpoint()`,
`RaftNode::advance_commit_index()`, `LedgerApplier::apply_checkpoint_entry()`

### Layer 4 — Evidence Verification (pq_verify)

```text
pq_verify ─→ signature ─→ canonical encoding ─→ Merkle root
         ─→ range ─→ previous checkpoint ─→ Raft term/index ─→ cross-node evidence
```

`pq_verify` independently reconstructs the evidence chain from on-disk
artifacts (`ledger.jsonl`, `checkpoints.jsonl`) and verifies:

1. **Signature:** ML-DSA-87 signature over `canonical_hash` matches the
   signer's public key fingerprint.
2. **Canonical encoding:** Checkpoint bytes match the canonical format.
3. **Merkle root:** `BLAKE3(seq || entry_data)` over the ledger range
   matches the checkpoint's `merkle_root` field.
4. **Range:** `ledger_entry_count == ledger_last_seq - ledger_first_seq + 1`.
5. **Previous checkpoint:** `previous_checkpoint_hash` links to the
   prior checkpoint's `checkpoint_hash` (chain continuity).
6. **Raft binding:** `raft_term` and `raft_log_index` match the committed
   log entry.

**Function:** `pq_verify::verify_checkpoints()`

## 5. Authoritative Metadata

### cluster_id

- **Type:** `String` (UUID v4)
- **Bootstrap:** Read from `VARDHAN_CLUSTER_ID` env var → persisted to
  `RaftPersistentState.cluster_id` → UUID v4 fallback if unset.
- **Authority:** Persisted and replicated via Raft log. All nodes must
  share the same value.
- **Function:** `RaftNode::with_config()`, `RaftNode::checkpoint_context()`

### config_epoch

- **Type:** `u64`
- **Bootstrap:** Loaded from persisted state → defaults to 1 if unset.
- **Authority:** Incremented on configuration changes, persisted and
  replicated. Included in every checkpoint.
- **Function:** `RaftNode::checkpoint_context()`

### Checkpoint Context Tuple

`checkpoint_context()` returns `(cluster_id, config_epoch, current_term, log_index)`.
This binds each checkpoint to its cluster, config generation, Raft term, and
log position — all necessary for replay and fork detection.

## 6. Key Design Decisions

### Checkpoint entries are NOT ledger entries

Checkpoint commands occupy Raft log positions but do NOT consume ledger
sequence numbers. This separation ensures:
- The audit chain (`LedgerBlock.index`) is contiguous and gap-free.
- Checkpoint commands don't interfere with ledger hash-chain continuity.
- `ledger_seq` (0-based, per regular entry) ≠ `raft_log_index - 1`

### Only ML-DSA-87 signing

Per SEC-EVIDENCE-002 requirements, only ML-DSA-87 (NIST FIPS 204) is used
for checkpoint signing. No RSA, no Ed25519 fallback.

### Only committed checkpoints are authoritative

Pending (uncommitted) checkpoints exist only in the leader's memory.
The `checkpoint_writer` is only updated in `apply_checkpoint_entry`, which
runs only after Raft quorum commit.

### MAX_FRAME_SIZE

Increased from 64 KB to 256 KB in `proxy_engine/src/transport.rs` to
accommodate the ~94 KB AppendEntries envelope containing a signed
checkpoint entry.

## 9. What P7.3 Does NOT Claim

This milestone does **not** assert:
- Live AWS/EKS/distributed deployment validation
- Real HSM/KMS integration or certification
- Byzantine fault tolerance beyond standard Raft (crash-stop model)
- Third-party penetration testing
- Production multi-region deployment
- Regulatory certification (FIPS 140-3, SOC 2, etc.)

P7.3 evidence is **engineering validation** via adversarial testing on a
local 3-node TCP cluster. It is not equivalent to independent security
review.
