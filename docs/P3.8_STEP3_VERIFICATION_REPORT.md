### Transport Path (real, not mocked)
```
RaftNode → RaftRpcClient → NetworkController → AeadTransport → TCP → RaftNetworkListener → RaftNode
```

### NetworkController (test-only fault injection)
- `NetworkController` struct wraps `Arc<dyn RaftRpcClient>` and injects faults **below** the RPC layer — NOT in production behavior.
- Methods: `block`, `unblock`, `delay`, `clear_delay`, `heal`
- Controls per-destination behavior: blocked destinations return `Err` immediately, delayed destinations sleep before forwarding.

### TestNode
- Wraps `Arc<RaftNode>` with additional test scaffolding.
- `killed: std::sync::atomic::AtomicBool` — set in `abort()`, used by `find_leader` / `count_leaders` / `count_candidates` to skip aborted nodes.
- `abort()` sets `killed=true`, aborts `run_handle`, `listener_handle`, `apply_handle`. Handler tasks spawned via `tokio::spawn` survive independently.

### RaftPeerManager::clear_worker
- Added to `ha_cluster/src/peer_manager.rs` — removes a peer's worker from the `workers: RwLock<HashMap<NodeId, Sender<PeerRequest>>>` cache, forcing fresh connection establishment on next RPC.

### Port Allocation
- Single tests: base = `19100 + run_id × 10`, nodes at `base+1/2/3`; restarted nodes use port `+1000` offset.
- 10× tests: `leader_crash` uses run_ids 100–109, `follower_crash` 200–209, `stale_rpc` 300–309, `partition_heal` 400–409. All well-separated (≥10 apart), no overlap with `raft_l3_replication.rs` ports (18101–18103).

### RaftConfig
- `fast_config()`: `{ election_timeout_min_ms: 150, election_timeout_max_ms: 300, heartbeat_interval_ms: 50 }` — used for single tests and 10× tests where no slow/stale peers interfere.
- `stability_config()`: `{ election_timeout_min_ms: 3000, election_timeout_max_ms: 5000, heartbeat_interval_ms: 200 }` — used for 10× tests where the 2s PeerManager RPC timeout can block `join_all`. Ensures election timeout > RPC timeout to prevent cascading elections.

### Key Constraints
- `submit_entry` does NOT deduplicate — idempotency is at the `LedgerApplier` level via `applied_requests: RwLock<HashMap<(String, String), u64>>`.
- Log entries are in-memory only (`Arc<RwLock<Vec<LogEntry>>>`).
- `persist_state` only persists `current_term` and `voted_for`.
- RPC response timeout: 2s (`timeout(Duration::from_secs(2), response_rx)` in `PeerWorker`).
- Leader broadcasts via `futures::join_all` — blocks on ALL peer RPCs before processing replies.

### Key Fixes During 10× Iteration

1. **Stale RPC 10× — "Multiple leaders" (line 1642)**
   - **Root cause:** After killing the leader, the new leader election produced a brief window where two alive nodes had `role=Leader` at different terms. The killed leader's `abort()` sets `killed=true` (skipped by `count_leaders`), but the surviving nodes briefly had two leaders before the old leader stepped down.
   - **Fix:** Replaced `find_leader` loop (returns first alive leader) with `wait_stable_leader_10x` which requires `count_leaders == 1 && count_candidates == 0` before returning. Also added `ELECTION_WAIT_STABLE` (20s) for `stability_config` elections (3-5s timeout range).

2. **Partition Heal 10× — "Minority didn't catch up"**
   - **Root cause:** After healing, the leader's `join_all` blocked for up to 2s (RPC timeout) while reconnecting to the minority. With `fast_config` (150-300ms election timeout), this triggered cascading leader elections — each new leader's `join_all` also blocked, perpetuating instability.
   - **Fix:** Switched to `stability_config()` (3-5s election timeout > 2s RPC timeout) so followers don't start new elections during the leader's `join_all` block. Combined with `clear_worker` (forces fresh PeerWorker connection) and a 2s post-heal sleep.

3. **Follower Crash 10× — 0/10 initially**
   - **Root cause:** After restarting the killed follower on a new port, surviving nodes' NetworkControllers still blocked the follower's old port. The restarted follower was invisible to the cluster.
   - **Fix:** After `restart_node`, call `unblock` on all surviving nodes' NetworkControllers for the restarted follower's old ID.

4. **`loose_config` (500-3000ms) abandoned**
   - The original `loose_config` with 500ms election timeout was insufficient — the 2s RPC timeout still exceeded the 500ms min election timeout, causing follower election timer expiry.
   - **Fix:** Replaced with `stability_config()` (3-3000ms → 3-5000ms) with `ELECTION_WAIT_STABLE=20s` to accommodate the longer election rounds.
