## 4. Supply chain and code quality analysis

- **Strict Clippy status**: `cargo clippy --workspace --all-targets -- -D warnings` passes cleanly with exit code 0 across the entire workspace (all libraries, tests, binaries, benchmarks, and examples). All blanket `#![allow(..., clippy::all, ...)]` suppressions have been eradicated from the integration test suites in `ha_cluster/tests/`, and all lints have been surgically remediated.
- **Financial arithmetic precision**: `payment_gate.rs` parses transaction amounts into exact integer minor units (`amount_minor_units: u128`) mapped against ISO 4217 currency scale exponents (e.g. USD/EUR=2, BHD=3, JPY=0). Binary floating-point representation drift is eliminated from limit checks and validation gates. Both `pacs.008.001.08` and `pacs.009.001.08` financial messaging schemas are validated with dual classical (Ed25519) and post-quantum (ML-DSA-87) signatures.
- **Enterprise Compose Secrets**: Hardcoded fallback database passwords (`vardhan_prod_secure_secret`) and default `DATABASE_URL` strings have been eradicated from `docker-compose.enterprise.yml`. Production deployments strictly require externally injected `POSTGRES_PASSWORD` and `VARDHAN_ADMIN_PASSWORD` secrets using `${VAR:?error}` fail-closed syntax. The guard script `scripts/check_enterprise_compose_secrets.sh` validates:
  1. Compose parsing fails closed when required production secrets are absent.
  2. Compose parsing validates cleanly when synthetic test secrets are supplied.
  3. Interpolated configurations contain zero predictable fallback secrets.
- **Runtime Acceptance Security**: The real-time acceptance suite (`scripts/verify_live_runtime.py`) operates with zero hardcoded credentials, resolving disposable admin credentials dynamically with fail-closed checking (`VARDHAN_ADMIN_PASSWORD` / `VARDHAN_ADMIN_PASSWORD_FILE`). It enforces full TLS validation (`ssl.CERT_REQUIRED`, `check_hostname=True`) against `https://localhost` using the configured CA trust anchor (`certs/caddy_local_root.crt`), eliminating insecure TLS bypasses.
- **E2E Lifecycle Validation Reconciliation**: `scripts/e2e_lifecycle_validation.py` was updated to dynamically generate unique finding identifiers per run and return deterministic exit codes (`0 if FAIL_COUNT == 0 else 1`), successfully passing all 33/33 lifecycle checks and resolving the discrepancy between historical test reports (31/31) and the README specification (33/33).
- **Workflow Consolidation & Staging Deployment Gating**: The duplicate workflow `platform-web.yml` was consolidated into `platform-web-contract.yml` running Node 22 with full frontend source sanity checks. `enterprise-release.yml` was updated to target `environment: staging` for artifact promotion, explicitly blocking automated production deployment and preventing spurious production deployment registrations until external banking certifications are evidenced.
- **Automated dependency audit**: Normal `cargo audit` and `cargo deny check advisories` pass under repository-configured exceptions. Newly published advisory RUSTSEC-2026-0387 for `crypto-bigint` was triaged: the direct dependency was upgraded to 0.7.7, and the legacy unpatched 0.5.5 transitive requirement from `saml-rs` was documented with an explicit, bounded exemption in `deny.toml` and `.cargo/audit.toml`.
- **Supplemental unfiltered audit**: Diagnostic scans outside repository exclusions continue to report legacy transitive dependencies (such as `rustls 0.21.12` pull-in by AWS KMS SDK, `h2 0.3.27`, `rsa 0.9.10`). These dependencies remain isolated in the opt-in KMS graph and require continued migration planning.
- **Secret scanning**: Both the repository secret pattern scan (`AKIA`, private key blocks) and the tracked secret guard script (`scripts/check_no_tracked_secrets.sh`) pass with zero findings. Historical commit triage identified non-sensitive public key fingerprints, test fixture keys, and parameter references.
- **SBOM**: A CycloneDX SBOM (`bom.json`) containing 554 components is maintained and validated.

## 5. Cryptographic and operational boundaries

- **ISO 20022 and Payment Identity**: Ingress validation enforces strict tenant-to-issuer binding (`DENY_ISSUER_UNBOUND`), authenticated BIC mapping via `InstitutionalKeyRegistry`, and rejects dynamic untrusted key substitution. Connection to an official banking PKI (X.509 CA federation / SWIFT BIC Directory) remains an external integration milestone.
- **Protocol Candidate Status**: AER-KEP-Q is an engineered protocol candidate designed for hybrid classical/post-quantum exchange; it has not undergone an independent peer-reviewed formal cryptographic audit or provable security evaluation.
- **FIPS 140-3 and Health Telemetry**: Cryptographic operations include internal Known Answer Test (KAT) health gates, Continuous Random Number Generator Tests (CRNGT), and Pairwise Consistency Tests (PCT). The control-plane health endpoint explicitly reports internal self-tests (`crypto_self_tests: "OPERATIONAL"`) as distinct from formal NIST CMVP validation (`fips_140_3_validation: "NOT_CERTIFIED"`, certificate: null). No claim of formal CMVP module validation is made.
- **Staging Network Security**: Edge proxy (`tls-proxy`), control-plane API, intelligence-plane, and database ports are bound strictly to loopback (`127.0.0.1`) by default (`${VARDHAN_BIND_IP:-127.0.0.1}`), preventing accidental exposure to public or shared network interfaces. Local staging health endpoints respond exclusively over loopback via TLS.
- **Database Restore and Recovery Benchmarks**:
  - *Small local test (baseline)*: Full restoration of a minimal 2-record dataset was measured at 81.71 ms RTO.
  - *Representative benchmark (10,000 transactions)*: Full transactional restoration of 20,100 entities (10,000 journal transactions, 100 accounts, 10,000 audit records; 12 MB database; 871 KB compressed archive) was executed into an isolated target database (`vardhan_rep_tgt`). Measured RTO was 432 ms (throughput: 46,527 records/second) with 100% financial amount checksum parity (1,860,185,000 minor units) and full index reconstruction verified.
  - *Real-time live concurrency drill*: 50 concurrent requests over verified TLS proxy completed in 33.71 ms (1,483.2 req/sec throughput, 0 errors, min 3.01 ms, mean 5.43 ms, p95 7.39 ms, max 8.09 ms).
- **Restart Recovery vs Automatic HA Failover**: Single-container stop/start testing is classified strictly as restart recovery. True multi-instance distributed coordination was verified across independent nodes sharing PostgreSQL (`multi_instance_concurrency_test`), proving atomic CAS single-winner election and cross-node duplicate prevention.
- **Durable Audit Trail**: Multi-process audit logging is protected by `fs2` exclusive file locking and trailing chunk seek. While verified locally and in CI under synthetic concurrency up to c=100, physical power-loss crash durability and distributed multi-datacenter replication remain unproven.

5. **Representative Database Restore Validation**: Completed. Empirically demonstrated 432 ms RTO on 10,000 synthetic transaction records with zero data loss or corruption.
6. **Live Runtime Security Verification**: Completed. Strict TLS verification (hostname check, test CA trust anchor) and disposable dynamic credentials enforced in real-time acceptance suite.
7. **Institutional Trust Registry & Production Key Custody (BLK-001)**: Requires completion of real production integration with institutional hardware security modules (PKCS#11 / AWS CloudHSM) and formal CA trust distribution.
8. **NIST CMVP FIPS 140-3 Module Certification (BLK-002)**: Requires formal accredited NVLAP laboratory evaluation and an issued NIST CMVP certificate.
9. **Independent Cryptographic Audit (BLK-003)**: Requires an independent cryptographic protocol review and security reduction of AER-KEP-Q by an accredited external security firm.
10. **Official ISO 20022 Counterparty Validation (BLK-004)**: Requires validation of supported payment profiles (pacs.008, pacs.009) against official ISO schemas in an authorised counterparty sandbox (SWIFT Alliance Lite2 / FedNow).
11. **Downstream Execution and Ledger Reconciliation (BLK-005)**: Requires connection of downstream execution handlers to core-banking ledger systems with automated two-phase reconciliation and recovery after ambiguous communication timeouts.
