# ADR-0004 — Blockchain Registry Design

**Status:** Accepted (pending approval)
**Date:** 2026-08-07

## Context
The architecture requires an on-chain registry of proof anchors plus the ability to gate
actions on a proved status, while keeping gas and auditability sane.

## Decision
Contract set in `packages/contracts` (Foundry):

1. **`ZKVerifierRegistry.sol`** — the **append-only** ledger:
   - `registerProof(circuitId, vkHash, proof, publicInputs)` → verifies Groth16 proof via
     the registered verifier for `circuitId`, then appends
     `keccak256(circuitId, vkHash, publicInputs, proof)` as a leaf.
   - Emits `ProofRegistered(uint indexed circuitId, bytes32 proofHash, address indexed prover, uint256 timestamp)`.
   - Keyed lookups: `getProofStatus(circuitId, publicInputHash)`.
2. **`VerifierFactory` / per-circuit verifier** — generated by snarkjs, deployed once per
   circuit, registered in the registry by an admin role.
3. **`ProofGatekeeper.sol`** — consumable hook for downstream contracts: requires a valid
   registry entry (status proved, not expired) before certain calls. This is the on-chain
   extension of the CI/CD gatekeeper model.

## Design rules (T5 mitigation)
- No external calls during `registerProof` beyond the precompile pairing check.
- Registry is append-only: no delete, no update of past entries; statuses only forward-
  transitioning.
- Checks-effects-interactions strictly followed; fuzz/invariant tests in Milestone 4.

## Consequences
- Auditable, replay-resistant (leaf keyed on inputs), gas-optimized single pairing check.
- The API's `verify` for chain-backed status reads the whitelisted contract.
- Multi-chain (DEBT-2) later: same ABI, different deployments.
